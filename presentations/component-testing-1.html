Why unit tests are not enough

  • Great for logic in isolation
  • Weak at integration seams
  • Mocks can hide real failures
Unit tests are still valuable. They are excellent for branching logic, pure transformations, and local error handling. The limit is that production failures often happen where modules, frameworks, serializers, ORMs, and external systems meet. Typical examples: wrong provider wiring in Nest, validation and serialization mismatches, ORM mapping issues, and stale assumptions about external API contracts.

LaunchPad example

  • POST /launches/:id/simulate
  • controller -> service -> Event Hub
  • consumer -> DB -> read API
Use this as the concrete example for the previous point. A unit test can prove that the service calls sendBatch or that a repository method was invoked. It cannot prove that the event is actually published, consumed, persisted, and then exposed back through the API. This is the gap between intent and working behavior.

Test pyramid vs. modern testing strategy

  • Classic: mostly unit tests
  • Modern: unit + component + integration
  • Component tests carry more confidence
The classic pyramid was a useful correction against expensive UI-heavy end-to-end suites. For backend services, the main shift is not abandoning unit tests but recognizing that many defects live in realistic module and infrastructure interactions. So a practical modern strategy uses unit tests for tight logic loops, component tests as the main confidence layer, and targeted integration or end-to-end coverage for critical flows.

Why the strategy changed

  • Backends are integration-heavy
  • Mocks are easy to overuse
  • Containers made realism cheaper
Expand here on why teams changed practice: services spend much of their time talking to databases, queues, SDKs, and upstream APIs; mocks are fast but can become self-fulfilling; and tools like Testcontainers reduced the cost of running realistic infrastructure in local development and CI. The real goal is confidence, not maximizing the count of tests.

A practical balance for Nest.js services

  • Unit: fast feedback on logic
  • Component: main confidence layer
  • Integration/E2E: critical paths only
If you want to elaborate, unit tests are best for pure logic and branching. Component tests are best for module-level behavior with real infrastructure boundaries. Integration or end-to-end tests are best for a few critical production flows and contract verification. For this course, component tests are the center of gravity.

Different layers of component tests

  • API layer
  • Database layer
  • Messaging layer
  • External-service boundary
API layer means exercising the Nest controller and service while replacing the upstream HTTP dependency with a realistic mock server. Database layer means running against a real PostgreSQL container so entities, repositories, and persistence behavior are tested together. Messaging layer means publishing and consuming real events through the Event Hub emulator. External-service boundary means controlling upstream responses precisely to test retries, mapping, and error handling.

How LaunchPad maps to those layers

  • GET /launches -> SpaceX API -> MSW
  • POST /favorite -> PostgreSQL -> Testcontainers
  • POST /simulate -> Event Hub -> containers

Takeaways

  • Unit tests are necessary, not sufficient
  • Component tests add realistic confidence
  • We will test API, DB, and messaging boundaries
