Why unit tests are not enough

  • Weak at integration seams
  • Mocks can hide real failures
Unit tests are still valuable. They are excellent for branching logic, pure transformations, and local error handling. The limit is that production failures often happen where modules, frameworks, serializers, ORMs, and external systems meet. Typical examples: wrong provider wiring in Nest, validation and serialization mismatches, ORM mapping issues, and stale assumptions about external API contracts.

LaunchPad as an Example

  • POST /launches/:id/favorite
  • controller -> service -> persistence layer
Use this as the concrete example for the previous point. A unit test can prove that the service calls a repository method or builds the expected payload. It cannot prove that a favorite is actually persisted and then exposed again through the read API. This is the gap between intent and working behavior.

A practical balance for Nest.js services

  • Unit: fast feedback on logic
  • Component: main confidence layer
  • Integration/E2E: critical paths only
If you want to elaborate, unit tests are best for pure logic and branching. Component tests are best for module-level behavior with real infrastructure boundaries. Integration or end-to-end tests are best for a few critical production flows and contract verification. For this course, component tests are the center of gravity.

What is a component in Nest.js?

  • A meaningful slice of behavior
  • Usually more than one class
  • Often a module, controller, or service with collaborators
Define component in a practical way, not dogmatically. In Nest, a component test usually means a controller with pipes, guards, and services wired up, or a service with real framework configuration around it. The key is that we test behavior at a seam users or neighboring systems care about, not just one class in isolation.

Component shapes you will test

Controller slice

HTTP request, validation, controller, service, response mapping

Service slice

Business logic with repositories, clients, and framework providers

Module slice

Several providers wired together as one feature boundary

Near-E2E slice

Nest app instance plus only a few controlled external seams

These are the shapes students should recognize in real projects. Near-E2E here means you still exercise the HTTP surface and most application wiring, but you may replace a payment gateway, queue publisher, or upstream REST client.

Unit vs. component: choose by risk

Question Prefer unit Prefer component
Mostly pure logic? Yes No
Framework wiring matters? No Yes
Serializer / pipe / guard behavior matters? No Yes
Mocks would hide the main risk? No Yes
Give students a decision rule. The more the risk comes from Nest wiring, DTO transformation, interceptors, provider configuration, or collaboration between classes, the more component tests earn their keep. If the value lies in fast feedback on dense branching logic, stay with unit tests.

Examples from a Nest app

  • Unit: map launch status to a display label
  • Component: GET /launches/:id through controller + service
  • Near-E2E: create Nest app and issue real HTTP requests
Keep the examples concrete. The first is a pure function. The second verifies a useful application slice. The third is what students should be able to assemble with TestingModule: most of the stack running, while replacing only the boundaries they do not want to hit for that test.

TestingModule is the core tool

  • Build a Nest app slice in memory
  • Choose which providers are real
  • Override only the seams you want to control
This is the transition into the practical section. TestingModule is how we control the realism level. We can compile a feature module, instantiate services directly, or create a full INestApplication and send requests into it.

Typical TestingModule flow

const moduleRef = await Test.createTestingModule({
  imports: [AppModule],
})
  .overrideProvider(Ll2Service)
  .useValue(mockLl2Service)
  .compile();

const app = moduleRef.createNestApplication();
await app.init();
Walk through the three decisions here: what module to import, what to override, and whether to get a service directly or create a Nest application. Emphasize that the override should target a real seam, not every collaborator by default.

Four ways to use it

Get a service

Fastest path for service-level component tests

Create an app

Exercise controllers through real HTTP requests

Import a feature module

Keep scope focused instead of booting the whole app

Override a provider

Swap one dependency without destroying the full slice

Students often learn only one pattern. Show that TestingModule supports a spectrum. They should pick the lightest harness that still exercises the risk they care about.

Example: get a service

TestingModule only wires DI

Compile DI, then get one provider.

import { Test } from '@nestjs/testing';
import { LaunchesService } from './launches.service';
import { Ll2Service } from './ll2.service';

const moduleRef = await Test.createTestingModule({
  providers: [LaunchesService, Ll2Service],
}).compile();

const service = moduleRef.get(LaunchesService);
await expect(service.findAll()).resolves.toHaveLength(3);

Exercise: src/tests-exercises/get-a-service.exercise.spec.ts

This is the lightest harness. The important point is that the TestingModule stops at DI compilation and we pull the service directly, so there is no Nest application instance and no HTTP surface involved.

Example: create an app

Same module, plus HTTP surface

Turn the module into an HTTP app.

import { Test } from '@nestjs/testing';
import request from 'supertest';
import { LaunchesModule } from './launches.module';

const moduleRef = await Test.createTestingModule({
  imports: [LaunchesModule],
}).compile();

const app = moduleRef.createNestApplication();
await app.init();
await request(app.getHttpServer()).get('/launches').expect(200);

Exercise: src/tests-exercises/create-an-app.exercise.spec.ts

The compile step is the same shape, but now we continue into createNestApplication because the controller, routing, and response behavior are part of what we want to verify.

Why mock Mongoose here?

Nest must resolve every constructor dependency

Even if this test only calls GET /launches, LaunchesService still depends on a Mongoose model.

import { Module } from '@nestjs/common';
import { getModelToken } from '@nestjs/mongoose';
import { LaunchMilestoneEvent, LaunchesService } from './launches.service';
import { Ll2Service } from './ll2.service';

const launchMilestoneEventModelMock = {};

@Module({
  providers: [
    LaunchesService,
    Ll2Service,
    {
      provide: getModelToken(LaunchMilestoneEvent.name),
      useValue: launchMilestoneEventModelMock,
    },
  ],
})
							class LaunchesFeatureModule {}

Why this token?

@InjectModel(LaunchMilestoneEvent.name) resolves through the Mongoose model token, not the raw string name.

What fails without it?

If that provider is missing, Test.createTestingModule(...).compile() fails before the app starts.

Why is an empty object enough?

This test does not hit the code path that uses the model methods, so DI only needs a placeholder.

When to use more?

If the test exercises persistence, mock the specific model methods or switch to a real database-backed slice.

This is the key clarification for students who wonder why a launches HTTP test needs any Mongo setup at all. The answer is DI, not behavior. Nest has to instantiate LaunchesService, and that constructor asks for a model. Because this particular test does not call the methods that use the model, an empty object is enough. If the test did exercise event persistence, then the fake would need the specific methods used by the service, or we would use a real database-backed slice instead.

Example: import a feature module

Narrow the slice up front

Boot only the feature under test.

import { Test } from '@nestjs/testing';
import { FavouritesModule } from './favourites.module';
import { FavouritesService } from './favourites.service';

const moduleRef = await Test.createTestingModule({
  imports: [FavouritesModule],
}).compile();

const service = moduleRef.get(FavouritesService);
await service.add('falcon-9');

Exercise: src/tests-exercises/import-a-feature-module.exercise.spec.ts

Here the key decision happens before compilation: import only the feature module instead of AppModule. That keeps the test fast and focused without changing how we access providers afterwards.

Example: override a provider

Swap one external seam

Keep the slice real, change one dependency.

import { LaunchesModule } from './launches.module';
import { Ll2Service } from './ll2.service';

const moduleRef = await Test.createTestingModule({
  imports: [LaunchesModule],
})
  .overrideProvider(Ll2Service)
  .useValue({ findAll: jest.fn().mockResolvedValue([mockLaunch]) })
  .compile();

This example changes the module after createTestingModule but before compile. That is the mental model to reinforce: same feature slice, one provider swapped so the test controls an external boundary without mocking everything else.

Selective mocking beats total mocking

  • Keep internal wiring real
  • Mock expensive or unstable boundaries
  • Avoid asserting implementation details
This is the key mindset. If every dependency is mocked, the test is just a dressed-up unit test. The value comes from keeping controllers, services, pipes, and response shaping real while mocking only the boundary that makes the test slow, flaky, or out of scope.

Where to keep real behavior vs. where to mock

  • Keep routing, validation, serialization, and feature services real
  • Mock upstream HTTP clients, publishers, and unstable SDKs first
  • Assert user-visible outcomes more than internal calls
Keep the behavior-producing layers real. That usually includes DTO validation, controller-to-service flow, error mapping, and most provider collaboration inside the feature. Mock external seams or side effects you intentionally do not want today. The principle is not anti-mock; it is mock at the right boundary and keep assertions focused on observable behavior.

Controller test pattern

  • Import feature module or declare controller + providers
  • Create INestApplication
  • Send requests with Supertest
This is the pattern for near-E2E checks inside one feature. You are not calling controller methods directly. You want the HTTP surface, framework glue, and response behavior involved.

Supertest 101

Supertest is a small library for making assertions against your HTTP server in tests.

import request from 'supertest';

const app = moduleRef.createNestApplication();
await app.init();

await request(app.getHttpServer())
  .get('/launches')
  .expect(200)
Keep this slide practical. Supertest sends real HTTP requests into the Nest app instance and lets us assert on status codes, headers, and response bodies.

Supertest 101 - continue

Common assertions check status, headers, and response body.

await request(app.getHttpServer())
  .post('/launches/falcon-9/favorite')
  .set('x-user-id', 'user-1')
  .expect(201)
  .expect('Content-Type', /json/)
  .expect(({ body }) => {
    expect(body.data.launchId).toBe('falcon-9');
  });
Show the three common categories: status code, header, and body assertion. Keep it concrete and avoid listing every API shape.

Service or module test pattern

  • Compile a module with the real providers you care about
  • Override only repositories, clients, or external tokens as needed
  • Verify the slice works together before asserting outbound details
Use this when HTTP is not the main risk or when behavior spans several providers inside the feature. It is often the best balance between confidence and setup size because Nest DI and configuration stay realistic while the harness remains lighter than a full app instance.

Common mistakes

  • Mocking every provider by habit
  • Calling controller methods directly for HTTP behavior
  • Asserting that mocks were called instead of user-visible outcomes
This slide should help reset instincts from unit-testing-heavy teams. Calling the controller directly skips the real Nest HTTP pipeline. Mock-call assertions check internals; prefer responses, saved data, or other user-visible outcomes. A component test should answer whether the slice works, not whether the test author predicted each internal call.
